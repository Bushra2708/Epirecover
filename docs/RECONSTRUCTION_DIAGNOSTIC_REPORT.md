## 1. Executive Summary & Observed Anomaly

When processing monument imagery, the application interface exhibited the following output:
- **Top Candidate**: `CAND-OCR-01` proposing reading `"44 4"`
- **Visual Evidence ($V$)**: `0.65`
- **OCR Evidence ($O$)**: `0.3378`
- **Linguistic Evidence ($L$)**: `0.3`
- **Historical Evidence ($H$)**: `0.5`
- **Retrieval Evidence ($R$)**: `0`
- **Final Ranking Score**: `0.3095`
- **Abstention Threshold**: `0.350`
- **Abstention Status**: Rejected / Abstained (with fallback candidate containing `[UNKNOWN]`)

While the abstention engine functioned correctly by rejecting a score below `0.350`, the candidate itself was completely nonsensical: ASCII numeric digits `"44 4"` were presented as a candidate reading for a classical Tamil stone inscription, accompanied by an unexplained `R = 0`.

This report provides the exhaustive diagnosis of the entire pipeline, from image intake to candidate display, separating confirmed defects from hypotheses.

## 2. Root Cause Analysis: The "44 4" Artifact

### 2.1 The OCR Failure Mode
- **Origin**: The text `"44 4"` is **raw OCR output** generated by EasyOCR running in English/Latin fallback mode (`easyocr-english-fallback`) on weathered lithic textures.
- **Mechanism**:
  1. On Windows environments under modern Python/PyTorch versions, the default EasyOCR Tamil detection/recognition weights frequently trigger state dictionary size mismatches or fail to load.
  2. When Tamil recognition fails, the engine falls back to the default English character inventory (Latin letters and ASCII digits).
  3. When an OCR engine configured for Latin characters is executed on raw stone cuts, chisel grooves, vertical cracks, and surface spalling, vertical strokes are misidentified as the numeral `'4'`, producing `"44 4"`.
  4. The engine reports a mean confidence of approximately `33.78%`.

### 2.2 The Candidate Generation Defect (Confirmed Defect D1)
- In `src/reconstruction/candidate_generator.py`:
  - Previously, `CandidateGenerator.generate()` inspected `raw_text = ocr_result.raw_text`.
  - It did NOT verify whether the recognized text actually belonged to the target script (Tamil Unicode block `U+0B80` to `U+0BFF`).
  - As a result, the Latin/ASCII noise `"44 4"` was wrapped directly into a `ReconstructionCandidate` with `candidate_id="CAND-OCR-01"` and `provenance=Provenance.OCR_PRED`.
- **Character vs. Stone Preservation**: The pipeline preserved raw OCR output without corrupting character bytes, but failed to filter out script-mismatched noise when English fallback occurred.

## 3. Mathematical Derivation of the 0.3095 Score

The multimodal fusion formula follows the EpiRecover architecture (PPT Slides 11, 12):
$$S(c) = w_V V + w_O O + w_L L + w_H H + w_R R$$

From `config/epirecover.yaml` (lines 98–104), the active configuration specifies:
- $w_V = 0.20$ (`visual_evidence`)
- $w_O = 0.25$ (`ocr_confidence`)
- $w_L = 0.15$ (`script_compatibility`)
- $w_H = 0.10$ (`source_quality`)
- $w_R = 0.30$ (`corpus_similarity`)

*(Note: $\sum w_i = 0.20 + 0.25 + 0.15 + 0.10 + 0.30 = 1.00$)*

### 3.1 Feature Decomposition for CAND-OCR-01
1. **Visual Score ($V = 0.65$)**:
   In `src/candidate_ranking/fusion.py`, `prov_weights[Provenance.OCR_PRED] = 0.65`.
   Because damage regions were minimal ($\le 2$), no damage discount was applied, yielding $V = 0.6500$.
2. **OCR Score ($O = 0.3378$)**:
   The OCR mean confidence was $33.78\%$, yielding $O = \frac{33.78}{100} = 0.3378$.
3. **Linguistic Score ($L = 0.3000$)**:
   In `fusion.py`:
   $$L = \min(1.0, 0.3 + 0.7 \times \text{tamil\_ratio})$$
   Because `"44 4"` contains zero Tamil Unicode codepoints, $\text{tamil\_ratio} = 0.0$, yielding:
   $$L = 0.3 + 0.7 \times 0.0 = 0.3000$$
4. **Historical Score ($H = 0.5000$)**:
   In `fusion.py`, the default neutral baseline is $H = 0.5000$. Because retrieval produced 0 records, no metadata comparisons occurred, preserving the neutral $0.5000$.
5. **Retrieval Score ($R = 0.0000$)**:
   No corpus records matched the query `"44 4"`, resulting in $R = 0.0000$.

### 3.2 Score Calculation
$$S(\text{CAND-OCR-01}) = 0.20(0.65) + 0.25(0.3378) + 0.15(0.30) + 0.10(0.50) + 0.30(0.00)$$
$$S(\text{CAND-OCR-01}) = 0.1300 + 0.08445 + 0.0450 + 0.0500 + 0.0000 = 0.30945 \approx \mathbf{0.3095}$$

Because the abstention threshold was set to $\tau = 0.350$, and $0.3095 < 0.350$, the abstention engine flagged this candidate for rejection.

## 4. Why Retrieval Returned R = 0 (Confirmed Defects D3 & D4)

### 4.1 Inability of Text Match on Noisy Query
- Querying a Tamil epigraphic corpus with `"44 4"` naturally yields 0 exact and 0 fuzzy character matches.
- In `src/evidence_retrieval/retriever.py`, a fallback mechanism was needed when text queries are unreadable or non-Tamil, allowing metadata (period, dynasty, monument) to retrieve relevant epigraphic context.

### 4.2 Overly Aggressive Script Gating & Default Language Parameter
Investigation uncovered two critical bugs in `src/evidence_retrieval/retriever.py`:
1. **Defect D3 (`language="tamil"` Default)**: `CorpusRetriever.retrieve()` had a default parameter `language="tamil"`. When unit tests or generic queries executed against multilingual fixtures (containing Prakrit, Sanskrit, or Brahmi), non-Tamil records were silently discarded before matching.
2. **Defect D4 (`_is_tamil_query` Gating)**: The method checked `self._is_tamil_query(query)` and required $\ge 10\%$ Tamil characters for *any* text retrieval. When queries were Latin-transliterated (such as `"piyadasi"`, `"arahata"`, or Romanized epigraphic transcripts), text retrieval was completely skipped, returning an empty result set `[]`.

## 5. Candidate Deduplication Collapse (Confirmed Defect D2)

In `src/reconstruction/candidate_generator.py`:
- The generator is contractually required to return multiple alternative candidate readings.
- When OCR output is empty or pure noise, the generator generates `CAND-UNK-01` (`[UNKNOWN]`) and appends `CAND-UNK-02` (`[UNKNOWN]`).
- However, the deduplication step:
  ```python
  seen: Dict[str, ReconstructionCandidate] = {}
  for c in candidates:
      key = c.candidate_text.strip()
      if key not in seen or c.confidence > seen[key].confidence:
          seen[key] = c
  ```
  keyed exclusively on `c.candidate_text.strip()`. Because both candidates had text `"[UNKNOWN]"`, one overwritten the other, collapsing the output to a single candidate.
